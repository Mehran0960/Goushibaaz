# Goushibaaz — Early Viral Video Scout

Goushibaaz is focused on one job: discover videos that are gaining momentum **before** they reach their viral peak, rank them using observed growth rather than total views alone, and provide a reliable foundation for publishing selected videos through independent destination adapters.

## Current architecture

- **Cloudflare Workers + Cron:** scheduled scans.
- **Cloudflare D1:** candidates, timestamped public-stat snapshots, trend scores, scan history, verified reuse authorization, and per-destination delivery state.
- **GitHub:** source control and a manual deployment workflow.

## How the scout ranks candidates

The current first source is YouTube Data API v3. The worker samples video statistics, stores snapshots, calculates views per minute and changes in that velocity, and ranks newer candidates with stronger growth. A first sighting is not treated as proof of growth; repeated observations are required.

The current discovery source is a signal, not a guarantee that a video will go viral. Additional sources can be added behind the same discovery interface.

The multi-source trend-intelligence pipeline keeps a free 15-minute discovery pass and adds a separate Firecrawl-backed pass every four hours. The paid pass rotates two searches per run and obeys the persisted internal ceiling of 800 credits/month; the six-runs/day schedule is sized for at most about 720 credits in a 30-day month, leaving a reserve. It reads `FIRECRAWL_API_KEY` from GitHub Actions Secrets (or a protected Actions variable fallback); missing credentials safely fall back to free discovery. Pexels is enabled separately through `PEXELS_API_KEY` in the shared publisher and Filo publisher; workflows log credential presence only, never the key value.

## Scheduled Persian-first Shorts scout

The GitHub Actions workflow `.github/workflows/discover-filo-candidates.yml` runs every two hours and can also be started manually. It dynamically crawls MediaFarsi home/ranking/new-channel/statistics pages, up to 100 sitemap targets at the first level, 150 additional sitemap targets, and up to 150 relevant category pages. It scans up to **1,000 Persian channel Shorts pages per run**: 100 priority channels plus a rotating window of up to 900 other discovered channels. Each run exports the complete discovered/selected channel registry in `out/mediafarsi-source-catalog.json`; URLs that fail or return no video cards are recorded as discovery errors rather than treated as active sources.

The additional public-source scout checks **28 fixed Telegram video channels plus up to 180 directory-discovered channels**, using 21 public Telegram directory/search pages; approximately **100 Aparat search queries** and **90 YouTube Creative Commons-filtered queries** cover Persian comedy, animals, visual entertainment, sports, food, nature, science, DIY, satisfying processes, and other short-form topics. Rotating public-web searches also cover Instagram Reels, TikTok, YouTube Shorts, X, Facebook Reels, Reddit, Vimeo, Dailymotion, Twitch clips and Rumble, with new metadata search lanes for **Snapchat Spotlight, Likee, Kwai and Bilibili**. These social-platform URLs remain discovery signals only; their video files are not downloaded or reposted without verified reuse rights. The scan runs with bounded concurrency to reduce burst failures. Repeated view snapshots are maintained in `state/trends.json` and `state/platform-trends.json`.

The shared policy lives in `config/content-policy.json`: **Iranian-audience fit and a strong entertainment hook rank first**, with measured growth, Persian/local relevance, freshness and topic diversity supporting the final choice. Priority lanes include Persian comedy, hidden-camera, reactions, surprise/payoff, sports skills, useful technology demos, food, transformations and other relatable entertainment. This content-priority model is adapted from the audience-triage approach in `TrendsUpLoader`; trends remain discovery signals, not permission to reuse. Every destination exports 9:16. Landscape sources are fitted in full over a blurred background; the foreground itself is not cropped. The scout writes `out/shorts-priority.json` and `out/shorts-priority.md` through `scripts/merge_short_candidates.cjs`, merging MediaFarsi Shorts, Telegram, Aparat, and YouTube leads into one shortlist shared for editorial review and future destination adapters.

All discovery data is metadata-only. Public Telegram/Aparat availability, a YouTube Creative Commons search filter, and trend rank do **not** grant permission to republish. A YouTube/API license label is still only a clearance signal until rights in the full clip (including music and third-party material) and the intended reuse are verified. These candidates stay discovery-only until rights are independently cleared. No discovery step downloads media or publishes a post.

View the [latest scout runs](https://github.com/Mehran0960/Goushibaaz/actions/workflows/discover-filo-candidates.yml).

## Filo: simple native-republication workflow

The native Filo republisher is a **separate publishing lane**. It discovers recent videos inside Filo and republishes only when the account-level and creator-level native permissions and all media/metadata requirements pass. It is not the shared Telegram/Bale/Rubika/Eitaa/Jetra video pipeline, and views or public visibility never imply permission.

The complete Persian project charter, safety gates, architecture, operational baseline, roadmap and mandatory change policy are maintained in [docs/FILO-NATIVE-REPUBLICATION.md](docs/FILO-NATIVE-REPUBLICATION.md). Every native-publisher code/configuration change must also be recorded in [docs/CHANGELOG.md](docs/CHANGELOG.md).

- Discovery is a bounded rolling scan of the current Filo category/tag feeds, not a crawl of the full historical catalog. The current implementation uses a 24-hour freshness window, up to 18 pages/category, a 112 category-page request ceiling, concurrency 4 and a four-minute category scan budget. It rotates up to four deep pages/category/cycle. A compact persisted 24-hour candidate catalogue reports unique recent feed videos, observed play/view changes and category distribution; every report must distinguish that observed count from full-feed coverage using `complete24HourCoverage`.
- Native Filo ranking retains the evidence order (measured play growth, measured view growth, cumulative counts, then freshness) and scores candidates with 68% measured momentum, 10% corroborated in-Filo topic demand (requiring at least two independently growing candidates), 12% fresh cross-platform topic trend, 8% soft preference for shorter duration, and 2% freshness. However, publication has a separate hard gate: at least three independent metric samples and positive measured velocity are required. Plays are primary. Views may be used when the play counter is absent, or when it is present but demonstrably stuck at zero across at least three independent samples; a nonzero but flat play counter is never bypassed. Acceleration is retained as a ranking bonus, not a hard eligibility requirement, so a fast, sustained upward trend is not rejected merely because its rate is no longer increasing. Cumulative counters and freshness remain diagnostic/ranking fallbacks only and cannot authorize publication. Cross-platform demand reuses the shared topic taxonomy and trend weights from `state/platform-trends.json`; explicit native Filo feed labels are bridged into the shared topic taxonomy, and missing or stale snapshots safely contribute zero. There is no local maximum-duration cutoff. An explicit account repost-quota response triggers a two-hour detail/publish cooldown, escalating to four/six hours if repeated within 24h, while discovery and momentum sampling continue. Internal posting pace is at least 20 minutes between operations, no more than 3 operations per rolling hour and 36 per rolling 24 hours; these are project safety budgets, not Filo's published numeric quota.
- The authoritative `detailGate()` requires Filo's global republish setting, no stop/limit flag, explicit `video.can_republish`, active/publishable source status, a non-deleted/non-restricted source, safe metadata, audio, monetization permission and a duration of at least 10 seconds. There is no local upper-duration cap; Filo remains authoritative on any platform-side limit. Title style/quality is a metadata preference, not an eligibility gate: safe rewrites are preferred, with sanitized source text or a neutral fallback used when necessary. Details are rechecked immediately before submission. Permission, audio, monetization, policy and account gates must never be weakened to increase volume.
- It publishes at most one video per run. The 36 operations/rolling-24-hour setting is an internal protective ceiling, not a Filo-published quota or a target. A pacing hold never stops fresh discovery or momentum sampling. When no fresh candidate passes the complete gates, the correct result is no publication in that cycle.
- Title generation aims for a concise 20–96 character result, but title style, distinctness or length within that editorial target is never an eligibility gate. Safe rewrites are preferred; otherwise sanitized source text or a neutral source-code fallback is used. The outbound payload guard remains 5–180 characters. Descriptions shorter than 30 characters after cleanup receive a neutral sentence grounded only in source metadata, not invented scene details. Known Filo title/description validation rejections may be retried once under the new metadata policy; access, permission, safety and other rejection types remain blocked. Ambiguous submissions are recorded as `submitted_unconfirmed` and are not blindly retried.
- The state ledger is `state/filo-native-republished.json`. Only `public_verified` with a verifiable public post counts as a real publication. Workflow success, successful tests, upload submission or a pending record do not count as a verified post.
- The checked-in workflow currently defines a GitHub Actions cron of `*/5 * * * *` plus `workflow_dispatch`. The separate Cloudflare Trend Scout Worker has a `*/10` cron in its checked-in config, but that does not prove it dispatches the Filo workflow. The older Cloudflare README describes a connector/bridge contract and must not be mistaken for proof of the current native publisher's live trigger. Verify live dispatch provenance before describing the scheduler as single-source or disabling a trigger.
- The publisher workflow's concurrency group serializes runs without cancelling an active run. Five-minute scheduling is best-effort; delayed Actions starts are possible.

See Filo's [publishing rules](https://ifilo.net/uploadRules) and [income rules](https://ifilo.net/calculatingIncomeHelp).

### Optional licensed stock-video supply: Pexels

- The shared Telegram/Bale/Rubika preparation path can use the official Pexels Videos API as an optional extra source. The adapter searches using the top currently observed trend lead; when no fresh lead exists it uses Pexels' popular-video endpoint. Pexels does not provide per-video view-velocity data through this integration, so no acceleration score is fabricated for stock clips.
- The API is polled at most once per 15 minutes for the shared publishing path and only when `PEXELS_API_KEY` is configured. Without that secret, the module returns an empty candidate list and Wikimedia Commons / Internet Archive discovery continues normally.
- The adapter accepts only Pexels-hosted video pages and HTTPS MP4 files, checks duration, audio, dimensions and relevance, credits the contributor and links to the original Pexels page and license. The output adds a Persian editorial title overlay, vertical composition and the channel end card; raw standalone stock reposting is not the intended use.
- Add the key in GitHub repository Settings → Secrets and variables → Actions → New repository secret, named `PEXELS_API_KEY`. Never put the key in source files or chat. A Pexels API key is not currently present in the repository, so this source remains inactive until that secret is added.
- Pexels has its own content and API rules. A public stock license does not clear third-party trademarks, people, privacy or other rights in every clip; candidates that fail validation are skipped.

## Multi-source trend intelligence

- A separate, free trend-intelligence workflow runs every **15 minutes**. To keep the higher refresh rate from multiplying polling load, it rotates **24 of 48** curated public Persian Telegram feeds per run (a complete pass about every 30 minutes) and **24 of 48** YouTube global-chart region/category buckets per run (a complete pass about every 30 minutes). It rotates Bing-indexed searches across Instagram, TikTok, YouTube, Aparat, X, Facebook Reels, Reddit, Vimeo, Dailymotion, Twitch, Rumble, Snapchat Spotlight, Likee, Kwai and Bilibili. The official YouTube Data API is used only when `YOUTUBE_API_KEY` is configured: search calls remain capped at **30/day**, spaced at least 48 minutes apart, while chart reads are rotated to preserve the existing request volume. Paid Firecrawl search is disabled in this adapter.
- Each 15-minute scan stores a bounded candidate/history ledger in `state/trend-intelligence.json`.
- Topic momentum is converted into `state/platform-trends.json`, which the existing editorial ranker already reads to adjust the next licensed-media selection. This makes viral demand a ranking signal rather than a shortcut around rights checks.
- Public-channel and social-platform candidates are discovery signals only. Their public availability, view counts, or source popularity do not grant permission to download or republish. Public publishing continues to require the existing verified CC0 / CC BY 4.0 / CC BY-SA 4.0 or explicit creator-permission gate.
- A successful first scan collected more than 200 fresh candidate records from Telegram feeds in one pass. Search engines and optional API lanes can return zero results or be unavailable; each source is best-effort and no single source is a hard dependency.

## Current publishing focus: five independent destinations

The project now uses a **single shared licensed-video preparation pipeline**. The central scheduler dispatches `.github/workflows/prepare-shared-video.yml`; it discovers a fresh entertainment candidate, verifies item-level commercial reuse rights and source audio, converts it once to an audio-preserving 1080×1920 (9:16) MP4, and creates one SHA-256-verified manifest/artifact. The full source frame remains visible in front of a blurred background instead of losing edge content to a center crop. Once an eligible artifact is uploaded, the preparation workflow dispatches Telegram, Bale, Rubika, Eitaa and Jetra separately with `workflow_dispatch`, passing the exact preparation run ID to each destination. Dispatch requests run concurrently; a failed request is recorded as deferred and never prevents the other destinations from starting. Each destination has its own adapter, concurrency group, credentials, deduplication and publication state; a failure in one destination cannot stop the other destinations or the next discovery slot.

- Rights-cleared discovery rotates bounded Wikimedia Commons and Internet Archive query batches on each shared-preparation slot, currently adding up to two leads from the measured trend ledger. A positive acceleration score is applied only to a licensed candidate whose source title strongly matches an observed rising-view lead. NASA/institutional public-media footage is deliberately disabled for this entertainment publisher. Every downloaded source is rechecked against its own CC0 1.0, CC BY 4.0 or CC BY-SA 4.0 metadata, public media URL, supported WebM/MP4 container, size, duration and audio-track presence before conversion.
- Editorial ranking follows the `TrendsUpLoader`-style Persian audience lanes, observed trend momentum, clear hooks and payoffs, freshness, local relevance and category diversity. Current-affairs, promotional, sensitive and weapons/military content is excluded from automated entertainment publishing; roundups are penalized. Scores never grant publication rights.
- Shared preparation and cross-destination dedupe: `scripts/rubika_publish_cc0.cjs`, `state/shared-publications.json`, and artifact `goushibaaz-shared-candidate`.
- Independent destination adapters: `scripts/telegram_publish.cjs`, `scripts/rubika_publish_shared.cjs`, `scripts/bale_publish.cjs`, `scripts/eitaa_publish_shared.cjs` and `scripts/jetra_publish_shared.cjs`. Telegram/Bale retain their shared transport; every other adapter has its own API contract, timeout handling, deduplication and state file.
- Destination state: `state/telegram-published.json`, `state/rubika-published.json`, `state/bale-published.json`, `state/eitaa-published.json` and `state/jetra-published.json`.
- The scheduler checks every five minutes (GitHub Actions' minimum scheduled interval) and aims to start the next shared preparation at that cadence. It can intentionally lengthen the interval when runner concurrency, GitHub API quota, missing external capacity data or repeated no-candidate outcomes make faster starts unreliable. An active preparation is rechecked after five minutes. GitHub may delay scheduled workflow starts, so this is a best-effort cadence rather than a real-time SLA. A slow or failed destination never blocks fresh discovery slots; only that destination's own workflow queue/retry path is affected. The capacity model budgets for preparation plus the three always-on destination runs, adding Eitaa and Jetra only when their credentials are configured. This avoids slowing the existing cadence before optional channels are connected; with all five destinations active, the planner can choose an eight-minute cadence to stay within the daily Actions-start ceiling.
- Telegram, Bale and Rubika currently retain their explicitly approved public-send gates. Eitaa and Jetra are dispatched only when their own provider/bot secret pairs are present; each destination then rechecks its credentials and uses the same two send-approval gates. Add `EITAAYAR_API_TOKEN`, `EITAAYAR_CHAT_ID`, `JETRA_BOT_TOKEN` and `JETRA_CHAT_ID` as GitHub Actions secrets only after creating/configuring each destination. Do not put tokens in source files or chat. This removes dependence on a shared repository variable. Each destination still resolves and validates its own bot/channel at send time, keeps its own idempotency ledger and concurrency group, and records success/failure independently.
- Telegram, Bale and Rubika resolve and validate their intended channel at execution time. Jetra validates the bot, channel/supergroup and administrator rights before upload. EitaaYar validates the bot via `getMe`; its documented send method uses `id_chat` (a configured public username without @ or the numeric destination ID).
- Each configured destination workflow explicitly requires the public-send and first-post approval gates. The adapter integration test runs all five adapters in dry-run mode against one identical artifact and sends no public messages.

Filo remains independently triggered by the Cloudflare dispatcher every five minutes (best-effort); the duplicate GitHub schedule is disabled. It does not block the shared Telegram/Rubika/Bale/Eitaa/Jetra publisher scheduler. No separate application-level cooldown is imposed; Filo's own native permission and upload-limit response is authoritative. The ledger allows up to 288 accepted or pending Filo submissions in any rolling 24-hour window when eligible videos are available.

### Destination availability

The currently wired public publishing destinations are **Filo, Telegram, Bale, Rubika, Eitaa and Jetra**. Eitaa is wired through the EitaaYar API (a provider interface rather than a native Eitaa bot endpoint); Jetra uses its native Bot API. Eitaa and Jetra workflows are credential-gated and remain skipped until their respective GitHub secrets are configured. Filo has its own native repost discovery and upload workflow with a five-minute best-effort schedule and no additional fixed application-level cooldown; it can make up to 288 attempts per UTC day, but only submits when a fresh video clears the reuse-rights and media checks. Telegram, Rubika, Bale, Eitaa and Jetra receive the same prepared artifact through five independent workflows with separate gates, concurrency groups, credentials and state files. Jetra's Bot API allows uploads up to 25 MB; if the shared MP4 exceeds that limit, only Jetra's adapter generates a smaller 720×1280 copy. The shared artifact and the copies sent to other destinations remain untouched. Telegram is an active automatic publishing destination with its own workflow, bot credentials, idempotency ledger and publication state; public Telegram channels also remain discovery sources. A delivery failure or timeout in one destination does not cancel the other destination or the next discovery slot. The shared preparation stage remains a common upstream dependency: when it produces no eligible artifact, its consumers send nothing.

YouTube and Aparat are currently **discovery sources only**, not upload destinations in this repository. The YouTube API key is used for search/statistics; a separate OAuth credential with the `youtube.upload` scope is required for the official upload API. Aparat has no uploader adapter in this repository; an official supported upload integration must be confirmed before adding an automated destination. Do not treat a discovered video source as a publication destination.

### Soroush Plus and additional platforms

Soroush Plus is not included in the automatic fan-out yet. The currently documented integration we could verify is Uniom's SoroushPlus **Account API**, which links a real Soroush+ account/session and exposes media-upload methods behind a third-party API. It is not the same as a native, first-party Soroush+ Bot API. Uniom lists a free tier of 3 connected accounts, 1,000 messages per month and 1 GB of traffic; that is useful for a proof-of-concept but not a safe assumption for a sustained, high-frequency video publisher. We will not connect a personal account session or introduce a third-party monthly dependency without a separate explicit approval. See [Uniom SoroushPlus integration](https://uniomi.ir/features/splus) and [its published quotas](https://uniomi.ir/pricing).

YouTube Shorts, Instagram Reels and Aparat remain future external publishing lanes. YouTube needs an OAuth credential with the upload scope (an API key used for discovery is insufficient); Instagram needs a Meta-authorized professional account and Reels publishing permissions; the repository does not yet have a verified Aparat upload adapter. We should add each only with its official account/API contract and an independent destination ledger—not through browser automation or personal-account scraping.

### Failure isolation and next-round handling

- Each shared publication round is tied to one preparation run ID. Telegram, Bale, Rubika, Eitaa and Jetra are dispatched independently only when that run contains a validated `prepared` manifest and its video artifact.
- A failed dispatch request or destination run ends only that destination's attempt. It does not cancel, wait for, or block the remaining destinations, Filo's independent schedule, or the next content-discovery round. There is no immediate same-round retry; the next scheduled round provides the next opportunity.
- Failures that occur before a send is attempted are recorded as retryable in that destination's own state file. An ambiguous submission after a send starts remains protected by the `send_started` / `submitted_unconfirmed` idempotency guard, so a possible successful post is not blindly duplicated.
- `no_eligible_candidate` and rights-based rejection remain content-selection outcomes, not destination outages. If there is no eligible shared artifact, no destination upload workflow is started for that round.

## Setup

1. Create or use a Google Cloud project with **YouTube Data API v3** enabled and obtain an API key.
2. Add `YOUTUBE_API_KEY` and a strong random `ADMIN_TOKEN` as **Cloudflare Worker secrets** for `goushibaaz-trend-scout`. Never commit them.
3. Add GitHub Actions secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` to enable the manual deployment workflow.
4. Run the `Deploy Goushibaaz trend scout` workflow from GitHub Actions.
5. Check `GET /health`; then use authenticated admin routes described in `cloudflare/README.md`.

## Security and reliability

- Secrets belong in Cloudflare/GitHub secret stores, never source files or logs.
- A trend score is based on observed data; missing history is marked as insufficient evidence.
- Duplicate candidates are keyed by platform video ID.
- Before a publisher sends media to a destination, the project should require verifiable authorization for commercial reuse and a valid, accessible media source.
- Destination publishing should be idempotent, independently retryable, and observable.
