# سند مرجع پروژه: بازنشر بومی مجاز فیلو

- **مخزن:** [Mehran0960/Goushibaaz](https://github.com/Mehran0960/Goushibaaz)
- **مسیر اجرایی:** `scripts/filo_native_republish.cjs`
- **گردش‌کار:** `.github/workflows/filo-native-republish.yml`
- **دفتر وضعیت و جلوگیری از تکرار:** `state/filo-native-republished.json`
- **گزارش هر اجرا:** `out/filo-native-republish.json` و Artifact همان اجرای GitHub Actions
- **تاریخ آخرین بازبینی این سند:** ۱۳ نوامبر ۲۰۲۶

این سند مرجع عملیاتی پروژه است. README فقط خلاصه‌ای از این سند است؛ در صورت اختلاف، کد و workflow فعال و سپس گزارش/دفتر همان اجرای واقعی ملاک‌اند. تغییرات رفتاری و عملیاتی باید در [دفتر تغییرات](CHANGELOG.md) ثبت شوند.

## ۱. هدف و محدوده

هدف این زیرپروژه، شناسایی و بازنشر **بومی در خود فیلو**ی ویدئوهای تازه‌ای است که در صفحه‌ها و فیدهای فیلو دیده می‌شوند و صاحب اثر/تنظیمات فیلو صراحتاً اجازهٔ بازنشر آن‌ها را داده‌اند. انتخاب باید بر پایهٔ رشد واقعی بازدید/پخش و تناسب مخاطب انجام شود؛ اما هیچ امتیاز، محبوبیت، عمومی‌بودن یا دیده‌شدن ویدئو جایگزین مجوز نیست.

این مسیر از خط لولهٔ آماده‌سازی و انتشار مشترک ویدئو برای تلگرام، بله، روبیکا، ایتا و جترا مستقل است. ابزار Cloudflare مربوط به جمع‌آوری روندها نیز به‌تنهایی اثبات‌کنندهٔ اجرای بازنشر بومی فیلو نیست. فایل قدیمی `cloudflare/README.md` دربارهٔ یک upload bridge قراردادی صحبت می‌کند؛ آن مسیر را نباید با workflow فعلی بازنشر بومی یکی دانست.

**نتیجهٔ مطلوب:** چرخه‌های پیوسته با تلاش برای بازنشر یک ویدئوی واجد تمام شرایط در هر نوبت ۱۷دقیقه‌ای، ثبت قطعی نتیجه، جلوگیری از ارسال تکراری و بدون انتشار اجباری هنگام نبود محتوای مجاز. **هیچ سقف داخلی ساعتی یا روزانه برای تعداد عملیات وجود ندارد.** فاصلهٔ ۱۷ دقیقه از آخرین عملیات، تنها pacing داخلی انتشار است؛ محدودیت واقعی اعلام‌شده از سوی خود فیلو با cooldown احترام‌آمیز اعمال می‌شود و دور زده نمی‌شود.

## ۲. اصول غیرقابل‌مذاکره

1. **مجوز صاحب اثر مقدم بر هر معیار دیگری است.** مجوز باید از فیلدهای معتبر و تازهٔ خود فیلو تأیید شود؛ عمومی‌بودن ویدئو، تعداد بازدید یا پیدا شدن آن در فید مجوز محسوب نمی‌شود.
2. **گیت جزئیات مرجع نهایی است.** پیش‌فیلتر فید فقط برای کاهش هزینهٔ جست‌وجو است. قبل از ارسال، اطلاعات جزئیات دوباره دریافت و گیت نهایی بلافاصله پیش از submit اجرا می‌شود.
3. **صدا و درآمدزایی الزامی‌اند.** ویدئوی بدون صدا یا فاقد مجوز درآمدزایی واجد شرایط نیست.
4. **هیچ خطایی با دور زدن محدودیت حل نمی‌شود.** مجوز بازنشر، محدودیت حساب، صدا، درآمدزایی، وضعیت انتشار و مدت مجاز نباید تضعیف شوند.
5. **ارسال مبهم تکرار نمی‌شود.** اگر نتیجهٔ submit روشن نباشد، وضعیت `submitted_unconfirmed` ثبت و پیش از هر تلاش مجدد تطبیق می‌شود.
6. **موفقیت فنی workflow معادل انتشار نیست.** فقط وضعیت `public_verified` و شناسه/نشانی عمومی قابل‌تطبیق، انتشار واقعی محسوب می‌شود.
7. **نبود نامزد واجد شرایط، نتیجهٔ عادی است.** در چنین چرخه‌ای هیچ ویدئویی منتشر نمی‌شود و چرخهٔ بعدی فرصت تازه‌ای برای بررسی است.

## ۳. معماری و چرخهٔ اجرا

### ۳.۱ کشف

اسکریپت فیدهای موضوعی/دسته‌ای فیلو را می‌خواند، کلیدهای برچسب زنده و شناسه‌های عددی را نرمال می‌کند و نامزدها را با کد یکتا، تازگی و متن پایه غربال می‌کند. فید، جزئیات کامل و مجوز قطعی را تضمین نمی‌کند.

پارامترهای فعلی در کد:
- پنجرهٔ پذیرش نامزد: ۷۲ ساعت؛ تاریخ نامعلوم یا آینده به‌عنوان تازه فرض نمی‌شود.
- حداکثر صفحات هر دسته: ۳۶.
- سقف کلی درخواست صفحه‌بندی دسته‌ها در هر چرخه: ۱۱۲.
- هم‌زمانی درخواست صفحه‌ها: ۴.
- بودجهٔ اسکن دسته‌ها: ۴ دقیقه.
- عمق‌خوانی چرخشی: حداکثر ۴ صفحهٔ عمیق برای هر دسته در هر چرخه؛ تعداد واقعی به وضعیت صفحه‌ها و بودجه وابسته است.
- فاصلهٔ حداقلی آغاز چرخه در منطق برنامه: ۴ دقیقه؛ این برای جلوگیری از هم‌پوشانی چرخه‌هاست و به‌معنای اجازهٔ بازنشر در هر چرخه نیست.
- فاصله‌گذاری بازنشر: حداقل و هدف عملیاتی ۱۷ دقیقه از آخرین عملیات؛ هیچ سقف داخلی ساعتی یا روزانه وجود ندارد. عملیات ردشده توسط فیلو و ارسال‌های `submitted_unconfirmed` نیز برای جلوگیری از تلاش شتاب‌زده، شروع‌کنندهٔ فاصلهٔ ۱۷دقیقه‌ای هستند.
- cadence اسکن/dispatch پنج‌دقیقه‌ای باقی می‌ماند (کمترین cadence بومی GitHub Actions). اگر چرخه در حداکثر پنج دقیقه مانده به پنجرهٔ بعدی آغاز شود، اجرای جاری تا لحظهٔ مجاز صبر می‌کند و سپس بررسی جزئیات و تلاش submit را ادامه می‌دهد؛ اگر زمان انتظار طولانی‌تر باشد، چرخه به نوبت زمان‌بندی‌شدهٔ بعدی موکول می‌شود. به این ترتیب فاصلهٔ ۱۷دقیقه‌ای به ۲۰ دقیقه گرد نمی‌شود، هرچند تأخیرهای خود GitHub همچنان ممکن‌اند.
- سقف داخلی تعداد بررسی جزئیات در هر چرخه، بودجهٔ اسکن و جلوگیری از هم‌پوشانی چرخه‌ها محدودیت پردازشی‌اند، نه سقف تعداد بازنشر در ساعت/روز.
- حداکثر بررسی جزئیات: ۹۰ نامزد در هر چرخه.
- کاندیدای تکراری/تلاش‌شده از دفتر وضعیت کنار گذاشته می‌شود.

این یک اسکن چرخشی و محدود از فیدهای فیلو است؛ **خزش کامل آرشیو یا تضمین پوشش تمام ویدئوهای تاریخی نیست**. نامزدهای دارای تاریخ معتبر فقط وقتی وارد رتبه‌بندی می‌شوند که سن محافظه‌کارانه‌شان حداکثر ۷۲ ساعت باشد. تاریخ Unix ثانیه/میلی‌ثانیه، ISO، شمسی و زمان نسبی پشتیبانی می‌شود. **نامزدهای فاقد تاریخ قابل‌اعتماد از صف مشاهده حذف نمی‌شوند**: برای سنجش رشد به‌صورت موقت نگهداری می‌شوند، اما فقط پس از سه نمونهٔ مستقل و سرعت مثبتِ اندازه‌گیری‌شده می‌توانند به بررسی جزئیات برسند؛ سن نامعلوم هرگز به‌عنوان «تازه» جعل نمی‌شود و امتیاز تازگی آن صفر است. timestamp آینده بیش از پنج دقیقه همچنان حذف می‌شود. گزارش `discovery.feedAgeDiagnostics` و `ageAdmissionPolicy` این وضعیت را جدا می‌کنند. جدا از این پنجرهٔ پذیرش، دفتر فشردهٔ پایدار `state.candidateCatalog24h` و گزارش `discovery.catalog24h` همچنان یک کاتالوگ تشخیصی مستقل ۲۴ساعته برای شمارنده‌های پخش/بازدید نگه می‌دارند؛ این عدد تعداد ویدئوهای **مشاهده‌شده در صفحات بررسی‌شده** است، نه کل جامعهٔ فیلو. کامل‌بودن اسکن پنجرهٔ عملیاتی از `completeLookbackCoverage` در `categoryCoverage` گزارش می‌شود؛ false بودن آن یعنی پوشش کامل ۷۲ ساعت اثبات نشده است.

ماژول تکمیلی جست‌وجوی سراسری ترندمحور در `scripts/filo_trend_search_worker.cjs` و `scripts/filo_global_search.cjs` نگهداری می‌شود. آداپتور صفحه‌بندی آن از قرارداد فعلی رابط فیلو استفاده می‌کند: `POST /api/v2/videos/search/{query}` با payload شامل `rowCount`, `page`, `needAllData` و `windowWidth`. پاسخ JSON متنی نیز پیش از نرمال‌سازی parse می‌شود. این worker در حال حاضر **زمان‌بندی فعال ندارد و خروجی‌اش به صف ناشر متصل نیست**؛ تا زمان تأیید اجرای احراز‌شدهٔ زنده، صحت صفحه‌بندی و رفتار دسترسی/مجوز، خروجی آن فقط دادهٔ کشف است و نمی‌تواند مجوز یا نامزد انتشار ایجاد کند.


### ۳.۲ امتیازدهی و انتخاب

- رتبه‌بندی امتیاز ترکیبی دارد: **۶۴٪ مومنتوم اندازه‌گیری‌شدهٔ خود ویدئو، ۱۰٪ تقاضای هم‌گروهی در فید فیلو، ۱۲٪ ترند موضوعی چندمنبعه، ۸٪ ترجیح نرم مدت کوتاه‌تر، ۲٪ تازگی و ۴٪ تناسب مخاطب**. تناسب مخاطب برای طنز/سرگرمی، آموزش کاربردی و چهره‌های شناخته‌شده امتیاز نرم دارد؛ این وزن‌ها جای گیت رشد یا مجوز را نمی‌گیرند.
- در لایهٔ رتبه‌بندی تشخیصی، نامزدهای دارای رشد پخش اندازه‌گیری‌شده بالاتر از رشد صرف بازدید، سپس شمار تجمعی پخش/بازدید و در نهایت fallback تازگی قرار می‌گیرند. این ترتیب به معنی اجازهٔ انتشار برای نامزدهای صرفاً تجمعی نیست؛ صف انتشار فیلتر مستقل و سخت شتاب را اعمال می‌کند.
- تقاضای موضوعی درون‌فیلو فقط وقتی امتیاز می‌گیرد که دست‌کم دو نامزد متمایز در همان feed tag/دسته وجود داشته باشند و **هر دو رشد اندازه‌گیری‌شدهٔ مثبت** داشته باشند؛ تعداد زیاد نامزد بدون رشد واقعی امتیاز تقاضا نمی‌سازد. سهم نامزدهای درحال‌رشد، میانگین سرعت/شتاب و وسعت گروه سپس امتیاز را تعیین می‌کنند.
- سیگنال بیرونی از `state/platform-trends.json` و تابع مشترک `buildTrendWeights()` در `scripts/quality_rank.cjs` خوانده می‌شود؛ طبقه‌بندی موضوعی نامزد فیلو با همان taxonomy مشترک انجام می‌شود تا موضوعات هم‌نام در منابع مختلف با هم مقایسه شوند. ورودی‌های Telegram، Aparat و YouTube CC با پنجرهٔ تازگی ۴۸ساعته مصرف می‌شوند؛ snapshot ناموجود، خراب، بیش‌ازحد قدیمی یا با timestamp آینده به امتیاز صفر تبدیل می‌شود و هرگز باعث توقف چرخه نمی‌گردد. برچسب‌های صریح دسته‌های بومی فیلو (از جمله آهنگ/موزیک‌ویدئو، طنز، فناوری، غذا، سفر، ورزش و حیوانات) به نزدیک‌ترین موضوع موجود در taxonomy نگاشت می‌شوند؛ دسته‌های مبهم به‌زور طبقه‌بندی نمی‌شوند.
- ترند چندمنبعه یک **سیگنال رتبه‌بندی** است، نه اثبات رشد خود ویدئو و نه مجوز بازنشر. پس از رتبه‌بندی، فقط نامزدهایی به بررسی جزئیات و انتشار راه پیدا می‌کنند که دست‌کم **سه نمونهٔ مستقل از همان شمارندهٔ منتخب** داشته باشند و سرعت معیار منتخب مثبت باشد. سرعت از رگرسیون خطی روی حداکثر **شش نمونهٔ معتبر اخیر** در تاریخچهٔ سه‌ساعته (با نگهداری حداکثر ۸ نمونه برای هر نامزد) محاسبه می‌شود؛ بنابراین ثابت ماندن شمارنده در آخرین بازهٔ پنج‌دقیقه‌ای، رشد مثبت و پایدارِ اندازه‌گیری‌شده در بازهٔ اخیر را به صفر تبدیل نمی‌کند. شمارندهٔ پخش معیار اصلی است. بازدید فقط در دو حالت جایگزین می‌شود: شمارندهٔ پخش اصلاً موجود نباشد، یا با وجود موجودبودن، در هر سه نمونهٔ مستقل آخر دقیقاً صفر و بدون تغییر مانده باشد (`playCounterZeroStalled`). شمارندهٔ پخش غیرصفر که رشد نکرده، همچنان معیار اصلی باقی می‌ماند و رشد بازدید نمی‌تواند از آن عبور کند. **شتاب مثبت امتیاز رتبه‌بندی را بالا می‌برد، اما شرط اجباری انتشار نیست**؛ نامزدی با سرعت رشد مثبت و پایدار هم می‌تواند انتخاب شود. شمار تجمعی بالا، ترند موضوعی یا تازگی نمی‌تواند گیت رشد را دور بزند.
- ترجیح مدت نرم است: ۱۰–۳۰ ثانیه بالاترین ترجیح، سپس ۳۱–۶۰، ۶۱–۱۰۰، ۱۰۱–۱۸۰، ۱۸۱–۶۰۰ و بیش از ۶۰۰ ثانیه با امتیاز کمتر. هیچ سقف محلی اضافه نشده؛ ویدئوی طولانی با رشد/تقاضای به‌مراتب بهتر همچنان می‌تواند انتخاب شود. حداقل ۱۰ ثانیه همچنان فقط در گیت قطعی جزئیات اعمال می‌شود.
- اولین مشاهده صرفاً baseline است؛ یک نمونه برای سرعت کافی نیست و دو نمونه فقط سرعت را نشان می‌دهند. سه نمونهٔ مستقل، سرعت را از روی تغییرات واقعی قابل‌اعتمادتر می‌کنند و شتاب دو بازهٔ پیاپی نیز برای رتبه‌بندی محاسبه می‌شود. اگر سرعت مثبت و پایدار باشد، صفر بودن شتاب به‌تنهایی مانع انتشار نیست؛ چون روند سریعِ ثابت هم می‌تواند بازدید زیادی بسازد.
- تناسب مخاطب فارسی/ایرانی و تنوع دسته ترجیح نرم‌اند، نه حذف خودکار دسته‌ها؛ رتبه‌بندی تناسب مخاطب فقط پس از حفظ ترتیب شواهد رشد اعمال می‌شود.
- تکرار موضوع فقط برای داستان مشخص و بسیار مشابه در پنجرهٔ ۴۸ ساعته محدود می‌شود؛ اشتراک صرف یک نام یا چهره دلیل کافی برای حذف نیست.
- اگر نامزد تازه، رشد مثبت یا مجوز/متادیتای قابل‌قبول ندارد، چرخه بدون انتشار بسته می‌شود.

### ۳.۳ متادیتا و کیفیت مناسب کشف

راهنمای رسمی فیلو بر عنوان جذاب اما کاملاً مرتبط، پرهیز از کپی عنوان منبع، توضیح جامع با جملهٔ اول قوی، پرهیز از تکرار و CTAهای بی‌ربط، موضوعات روز و پرطرفدار، تازگی و کیفیت تأکید دارد. بر همین اساس:
- ایموجی‌های تزئینی، نشانه‌گذاری تکراری و کشیدگی مصنوعی حروف از عنوان پاک می‌شوند؛ موضوع و کلیدواژهٔ واقعی حفظ می‌شود.
- عبارت‌هایی مانند «نظر خود را بنویسید» به‌تنهایی عنوان محسوب نمی‌شوند؛ عنوان باید موضوع واقعی ویدئو را توصیف کند.
- توضیح از متن واقعی منبع پاک‌سازی می‌شود؛ CTAهای تبلیغاتی/تعامل‌گیری، پیوند و هشتگ حذف و جمله‌های تکراری یک‌بار نگه داشته می‌شوند. جملهٔ آغازین مرتبط حفظ می‌شود.
- متن جایگزین فقط از عنوان/شرح واقعی منبع ساخته می‌شود؛ صحنه یا ادعای حدسی اضافه نمی‌شود.
- عنوان، توضیح یا امتیاز ترند هیچ‌گاه مجوز انتشار ایجاد نمی‌کند؛ گیت جزئیات فیلو مرجع قطعی است.

منابع رسمی: [قوانین کاربری فیلو](https://ifilo.net/userRules) و [راهنمای افزایش درآمد و کیفیت ویدئو در فیلو](https://ifilo.net/calculatingIncomeHelp).

### ۳.۴ گیت قطعی جزئیات

تابع `detailGate(root, video)` در `scripts/filo_native_republish.cjs` مرجع تصمیم نهایی است. از جمله کنترل می‌کند:

- `root.is_republish === true`

- پاک‌سازی نشانی اینترنتی، هشتگ، شناسهٔ کاربری و عبارت‌های دعوت به تعامل انجام می‌شود؛ وجود لینک در عنوان خام به‌تنهایی باعث رد ویدئو نیست.

## ۵. زمان‌بندی و هم‌زمانی

اگر endpoint جزئیات فیلو خطای صریحِ اتمام سقف بازنشر حساب بدهد، ناشر آن را خطای سراسری حساب تشخیص می‌دهد و درخواست‌های جزئیات/ارسال را متوقف می‌کند؛ در این فاصله فقط کشف فید و نمونه‌برداری رشد ادامه می‌یابد. نخستین پیام سهمیه cooldown دو ساعته می‌دهد؛ تکرار پیام در ۲۴ ساعت، backoff را به چهار و سپس حداکثر شش ساعت افزایش می‌دهد. این بازه‌ها سیاست محافظتی داخلی‌اند و ادعای زمان دقیق reset فیلو نیستند. در نخستین چرخه پس از استقرار این اصلاح، اگر دفتر قدیمی cacheهای ۴۰۳ نامزدها را داشته باشد، فقط یک مورد از بالاترین نامزدهای رتبه‌بندی‌شده برای یک استعلام واقعی آزاد می‌شود؛ باقی cacheها حفظ می‌شوند. این مهاجرت یک‌باره است و از پاک‌سازی دسته‌جمعی ۴۰۳های واقعیِ مختص هر ویدئو جلوگیری می‌کند.

Workflow فعال در main در حال حاضر این محرک‌ها را تعریف می‌کند:
- GitHub Actions schedule با cron برابر `*/5 * * * *`.
- اجرای دستی از طریق `workflow_dispatch`.
- اجرای اعتبارسنجی و تست در Pull Requestهای دارای مسیرهای مرتبط.

گروه concurrency برای اجرای publisher، اجرای فعال را لغو نمی‌کند و از دو submit هم‌زمان جلوگیری می‌کند. اسکریپت حداقل فاصلهٔ چهار دقیقه‌ای آغاز چرخه‌ها را برای جلوگیری از هم‌پوشانی حفظ می‌کند. فاصلهٔ ۱۷ دقیقه‌ای بین عملیات بازنشر مستقل از cadence کشف است؛ اگر اجرای پنج‌دقیقه‌ای پیش از لحظهٔ مجاز برسد و حداکثر پنج دقیقه تا موعد مانده باشد، تا همان موعد منتظر می‌ماند. محدودیت زمان‌بندی GitHub و تأخیر احتمالی شروع اجرا پابرجاست؛ این SLA قطعی نیست. هیچ سقف داخلی برای عملیات ساعتی یا روزانه اعمال نمی‌شود.

**ابهام زمان‌بندی خارجی:** README قدیمی‌تر ادعا می‌کرد Cloudflare dispatcher محرک یگانه است و schedule بومی GitHub غیرفعال است؛ این ادعا با workflow فعلی که cron فعال دارد سازگار نیست. در نمونهٔ اخیر اجراها، رویداد آخرین اجراها `workflow_dispatch` بوده و در شش اجرای native اخیرِ بررسی‌شده، رویداد `schedule` مشاهده نشد؛ بنابراین cadence پنج‌دقیقه‌ای ثبت شده، اما caller واقعی dispatch از خود این گزارش‌ها معلوم نیست و ممکن است دستی یا خارجی باشد. فایل Worker در `cloudflare/wrangler.jsonc` یک cron ده‌دقیقه‌ای برای Trend Scout تعریف می‌کند، اما این به‌تنهایی ثابت نمی‌کند که Worker هنوز workflow فیلو را dispatch می‌کند. تا زمان مشاهدهٔ لاگ/پیکربندی زندهٔ dispatch، نباید منبع محرک را قطعی معرفی کرد. قبل از حذف هر محرک باید هم‌پوشانی و رفتار واقعی آن اندازه‌گیری شود.

## ۶. وضعیت‌ها و شواهد انتشار

دفتر `state/filo-native-republished.json` شناسهٔ منبع، شناسهٔ ویدئوی بازنشرشده، لینک عمومی، زمان و وضعیت هر تلاش را نگه می‌دارد.

## ۷. خطاها و داده‌های تشخیصی

1. **تکمیل telemetry جزئیات:** دلیل دقیق رد/عدم انتخاب هر نامزد و خطای دریافت جزئیات، مجوز، صدا، درآمدزایی و مدت به‌صورت جدا گزارش شود.
2. **پایش عملکرد پست:** در صورت شناسایی شمارندهٔ معتبر فیلو، بازدید/پخش هر پست عمومی در ساعت‌های ۱، ۳ و ۲۴ ثبت شود؛ تا آن زمان هیچ عدد تخمینی به‌جای آمار واقعی گزارش نشود.
2. **تشخیص 403 و cooldown:** پیام پالایش‌شده و نوع خطا در artifact باشد؛ اطلاعات ورود و نشست حذف شوند.
3. **پوشش ۲۴ ساعته:** معیار `complete24HourCoverage` با بررسی ترتیب صفحه‌ها، cursorها و خطاهای pagination قابل‌اتکا شود؛ صرف افزایش تعداد درخواست‌ها کافی نیست.
4. **متادیتای فارسی:** تست رگرسیون برای عنوان‌های زیر ۱۰۰ کاراکتر، عنوان خیلی کوتاه و توضیح بیش‌ازحد کوتاه/تهی گسترش یابد؛ متن ساختگی یا پرکننده تولید نشود.
5. **reconciliation ارسال مبهم:** مورد `submitted_unconfirmed` تا حصول نتیجهٔ قطعی پیگیری شود و پیش از آن دوباره ارسال نشود.
6. **زمان‌بندی دوگانه:** وجود/عدم وجود dispatcher خارجی با لاگ و تنظیمات استقرار اثبات شود؛ محرک فعال بدون شواهد حذف یا تکثیر نشود.
7. **پایش روزانه:** گزارش کوتاه باید آخرین انتشار واقعی، آخرین چرخه، مانع اصلی، خطاها و PR/Run مربوط را پوشش دهد؛ حتی در روزهای بدون تغییر.

## ۱۱. الزام مستندسازی و کنترل PR

این قاعده جزئی از فرایند توسعه است، نه توصیه:

- هر تغییر کد، تست، workflow، زمان‌بندی، قرارداد API، گیت مجوز، رتبه‌بندی، عنوان/توضیح، ساختار state یا رفتار reconciliation در محدودهٔ بازنشر بومی، باید ورودی جدید در `docs/CHANGELOG.md` داشته باشد.
- ورودی باید تاریخ، فایل/بخش، مسئله یا دلیل، رفتار قبل/بعد، اثر عملیاتی، تست/شواهد و لینک PR/commit را ذکر کند.
- تغییر هدف، معماری، گیت‌ها، حدود، قرارداد داده یا roadmap باید علاوه بر changelog، همین سند مرجع را به‌روزرسانی کند.
- تغییر باید در شاخهٔ مجزا و از طریق PR انجام شود؛ اجرای تست رگرسیون مرتبط الزامی است.
- workflow بررسی PR تغییر کد اصلی یا تنظیمات native publisher را بدون تغییر `docs/CHANGELOG.md` رد می‌کند.
- ثبت خودکار هر اجرای معمولی در ledger، تغییر عملیاتی داده است و نیاز به یک changelog انسانی برای هر چرخه ندارد؛ اما تغییر در منطق تولید/تفسیر ledger باید مستند شود.
- هیچ توکن، رمز، cookie، session، دادهٔ شخصی یا بدنهٔ حساس پاسخ API در اسناد/گزارش عمومی ثبت نشود.

#### محدودیت دسترسی در الزام نهایی ادغام

کنترل PR و الگوی PR در مخزن اضافه شده‌اند و job اعتبارسنجی در PR باید در صورت نبود ورودی changelog شکست بخورد. بااین‌حال، تلاش برای خواندن تنظیمات Branch Protection شاخهٔ `main` از طریق اتصال GitHub با پاسخ 403 (`Resource not accessible by integration`) رد شد. بنابراین فعال بودن یا نبودن الزام status checkها و جلوگیری از push مستقیم **تأیید نشده** است. برای الزام غیرقابل‌دورزدن، maintainer مخزن باید در GitHub Settings → Branches یا Rulesets، ادغام به `main` را منوط به Pull Request و موفقیت check با نام `Filo native authorized republisher / validate` کند و push مستقیم را محدود کند. تا آن زمان، guard در PR موجود است ولی نمی‌توان ادعا کرد تنظیمات branch protection هم enforce شده‌اند.

## الگوی ورودی changelog

```markdown
## YYYY-MM-DD — عنوان تغییر
- محدوده: فایل‌ها/ماژول‌ها
- دلیل: مسئلهٔ قابل‌مشاهده و شواهد
- تغییر: رفتار قبل و بعد
- ایمنی/مجوز: گیت‌های مرتبط و تأیید عدم تضعیف آن‌ها
- آزمون: فرمان‌ها و نتیجهٔ واقعی
- اثر عملیاتی: انتشار واقعی/بدون انتشار/نیازمند پایش
- مرجع: PR، commit و Run
```

**اصل پایانی:** آنچه در سند نوشته می‌شود باید از main، کد، گزارش همان اجرا یا PR قابل‌ردیابی باشد. هیچ اقدام انجام‌نشده، انتشار تأییدنشده یا رفع مشکل اثبات‌نشده نباید به‌عنوان واقعیت ثبت شود.
